# ranobeNext 要件定義書

ライトノベル推薦・検索アプリ「Ranobe Finder」を Next.js で作り直すための要件定義。
今の実装: `/Users/kei/Downloads/ライトノベル` (Vite + React SPA + FastAPI + Supabase)。

- 作成日: 2026-10-13 / 更新: 2026-10-15
- ステータス: ドラフト (§10 の未決事項を確定させてから実装に入る)

**2026-10-15 の方針変更**
- **自然言語検索 (AI 検索) は作らない**。検索は「タグで絞り込む + キーワード」だけにする
- **似ているシリーズ**は、ジャンルタグが2つ以上同じ作品に絞り、theme / mood / reader の3観点のベクトルで並べる。結果は保存せず、**呼ばれるたびにその場で計算する**
- その場で計算できるように、3観点のベクトルとジャンルだけを持つ細いテーブル `series_vectors` (約151MB) を分けた。Supabase は Micro (共有バッファ 256MB) で、1.7GB の `openbd_test_series` から読むと数秒〜タイムアウトになったため (architecture.md §4.3)
- 実測 (2026-10-15): 似ているシリーズは中央値 0.16秒 / p95 0.32秒 (キャッシュが温まった状態)。手元で同じルールを計算した結果と 100% 一致

## 1. 背景と目的

### 1.1 今の課題

| 課題 | 詳細 |
|---|---|
| ベクトル検索がサーバーレスで動かない | 6観点 × 3072次元のベクトルを `backend/data/vector_cache/facets.npz` (約578MB) に置き、FastAPI プロセス内の numpy で全件の cosine を計算している。Vercel には載らない |
| 類似作品・あなたへのおすすめが Vercel で空になる | 環境変数 `VERCEL` があると空配列を返している |
| 3072次元に DB インデックスを張れない | pgvector の HNSW / IVFFlat は、`vector` 型だと 2000次元が上限。そのため 031 でインデックスを全部 DROP した |
| 構成が二重 | SPA (Vite) と API (FastAPI) が別々にデプロイされている。Azure VPS + Caddy の運用も必要 |

### 1.2 目的

1. フロントエンドと API を **Next.js (App Router) 1つにまとめ**、Vercel だけで全機能を提供する
2. 6観点のベクトルを **1536次元** に戻す (実施済み。HNSW インデックスも作成済み)
3. インメモリのキャッシュ (npz) と VPS をなくし、類似作品とおすすめを本番で動かす
4. 詳細ページを SSR/ISR にして、SEO と初回表示を良くする

### 1.3 スコープ

| 対象 | 対象外 |
|---|---|
| 検索アプリ全体 (画面 + API) | 書誌収集・Gemini エンリッチなど Python のデータパイプライン (`backend/scripts/`) は今のまま残す |
| ベクトル列の 1536次元化 (実施済み) | パイプラインの TypeScript への移植 |
| 似ているシリーズ・おすすめ用の細いテーブル (`series_vectors`) | 自然言語検索 (AI 検索) |
| 検索と推薦を SQL 関数 (RPC) に移す | 旧 `series` / `volumes` / `tweets` テーブルの DROP |
| 埋め込み生成スクリプトの 1536 対応 (Python 側の最小限の改修) | 新しい推薦アルゴリズムの研究 |

## 3. 機能要件

画面と見た目は、claude.ai Design の案 A「グリッド」に合わせる ([ui-design.md](ui-design.md))。今の機能のうちデザインにないものは、ui-design.md §4 の方針で足すか外す。

### F1. ホーム (`/`)
- **あなたへのおすすめ** (ログイン時): お気に入りと読了をもとにした推薦を6件。カードごとに**推薦理由のラベル**を付ける (ui-design.md §5)
- 未ログイン時は、同じ場所にログインを促すパネルを出す
- **新作・新刊**: 最近 (今日から30日前〜今日、JST) 発売された親シリーズから**ランダムに12件**選ぶ。表示するたびに入れ替わる。「10/10(土) 発売 · 全3巻」の形で表示する。範囲内が12件に満たないときは、新しい順の上位100件から選ぶ
- **新刊カレンダー** (案 B の表): 同じ候補を発売日の新しい順に表で出す (列は 発売日 / 書影 / タイトル・著者 / レーベル / 巻数)。最初は30行で、「さらに見る」で30行ずつ足す。発売予定 (未来の日付) は含めない
- 今の「おすすめの定番」と「話題沸騰中」はデザインにないので外す (`popularity_score` / `momentum_score` のデータは残し、並び順に使う)
- 対象は親シリーズだけ (`parent_series_id IS NULL`)。F2・F3 も同じ

### F2. さがす: 一覧と絞り込み (`/search`)
- 件数と「すべてのシリーズ」の見出し
- 絞り込みの表: ジャンル / 雰囲気 / サブジャンル。チップには**入力した語だけで絞った集合での件数**を出す (選んだタグには左右されない)。0件のチップは押せなくする
- 複数タグの条件: AND / OR を切り替える。3つの分類すべてに同じ条件がかかる
- 並び順: 新しい順 (初期値) / 人気順 / タイトル順
- 表示: 書影 (最初はこれ。マウスを乗せると作品名・著者・発売日・巻数が出る) / リスト
- 「条件をリセット」
- ページ送り: 48件ずつ「さらに見る」で追加する
- 条件はすべて URL クエリに持つ (共有したり、戻るボタンで元に戻したりできる)
- 6軸スコアのスライダーは外す (データは残す)

### F3. キーワード検索 (ヘッダーの検索欄、入力に合わせて絞り込む)
- 入力すると「さがす」に移り、300ms 待ってから結果を絞り込む
- 対象: タイトル・著者・イラストレーター・レーベル・あらすじの部分一致 (`pg_trgm`) と、タグ名の一致
- 絞り込みの表やチップの件数とも連動する
- **自然言語検索 (AI 検索) は作らない** (2026-10-15 決定)。LLM もクエリの埋め込みも使わない

### F4. (欠番: 自然言語検索は作らない)

### F5. シリーズ詳細 (`/series/[id]`)
- 「← 検索結果に戻る」(前の条件を残して戻る)
- 書影、メタ情報 (レーベル / 全N巻 / 最新刊の発売日)、作品名、著者 / イラスト
- タグの表 (ジャンル / 雰囲気 / サブジャンル)。押すと、そのタグで絞り込んだ「さがす」に移る
- 「お気に入りに追加」「読み終わった」(どちらもオン / オフだけ。評価は付けない)。未ログインならログイン画面に移る
- あらすじ
- 巻一覧 (巻・書影・タイトル・発売日の表)。特装版は本編の行に「特装版あり」と出し、上中下は巻の番号に添える。10巻を超えたら残りは折りたたむ。デザインにはないので、あらすじの下に足す (ui-design.md §3.3.1)
- **似ているシリーズ** 6件 (F8)。カードごとに共通点のラベル (同じ著者 / 共通ジャンル) を付ける
- 表紙は、カバーのある最新巻のものを使う
- SSR/ISR と `generateMetadata` で OGP に対応する
- 6軸スコアの棒グラフ、観点別の紹介、サブシリーズはデザインにないので外す (データは残す)

### F6. 著者で絞り込む
- 著者ページは作らない。詳細ページの著者名を押すと `/search?author=` に移り、その著者の作品で絞り込む

### F7. 認証 (`/auth`)
- Supabase Auth のメールアドレス + パスワード (サインイン / サインアップ)
- サインアップ時に表示名を入力すると、trigger で `profiles` に入る (今ある 022)
- `@supabase/ssr` で Cookie セッションにし、Server Component でもログイン状態を判定する
- 画面はデザインにないので、デザインのトークンと部品を使って新しく描く

### F8. 似ているシリーズ (2026-10-15 に決めたルール)
- **候補**: ジャンルタグ (`genre_tags`、24種) が**2つ以上同じ**作品。基準作品のジャンルが1つだけなら、1つ同じでよい。ジャンルが無い作品は絞らない
- **並び順**: **theme / mood / reader の3観点**のベクトルで近い順。観点ごとに cos を**候補の中での順位** p (0〜1) にし、Σ (p + p²) で合成する (合成方法は今の実装と同じ)。plot / cast / review は使わない
- **その場で計算する**: RPC `similar_series` が、`series_vectors` から候補を GIN インデックスで絞って毎回計算する。結果は保存しない
- 「全件の中での順位」で付けた場合との一致率は、手元の試算で平均 92%
- 共通点のラベル用に、同じ著者かどうかと、共通ジャンルを返す
- 今の実装 (一番珍しいジャンルで絞り、6観点で並べる) とは結果が変わる。たとえば百合作品の「似ている」に、ジャンルが2つ同じ普通のラブコメも入るようになる

### F9. マイページ (`/account`、ログイン必須)
- 画面はデザインにないので、新しく描く。ヘッダーのアバターと名前から移れるようにする
- お気に入りの一覧と読了の一覧。`list` カードで表示する (評価は扱わない。`read_series.rating` 列は残す)
- プロフィール: 表示名、自己紹介、好みのジャンル・雰囲気

### F10. あなたへのおすすめ
- 元にする作品: ログインユーザーのお気に入りと読了 (それぞれ最新50件)
- 3観点それぞれで、元にした作品の平均ベクトルを作る (cos の平均は、平均ベクトルとの内積に等しい)。全件 (元にした作品を除く) について近さを計算し、F8 と同じ合成で並べる。ジャンルでは絞らない
- その場で計算する (実測: 8作品から中央値 0.22秒)

## 4. ベクトルの要件 (1536次元)

### 4.1 次元とモデル

| 項目 | 決定 |
|---|---|
| 次元数 | **1536** (実施済み) |
| モデル | **`text-embedding-3-large` に `dimensions=1536` を指定** |
| 正規化 | L2 正規化して保存する |

- 3072 から 1536 への変換は、先頭から切り詰めて L2 正規化するだけで、`dimensions=1536` で埋め込み直したものと同じになる (実 API で確認済み。cos 平均 0.99987)。そのため、再埋め込みはしていない
- 今後 `*_text` を更新したときは、`dimensions=1536` を付けて埋め込む

### 4.2 スキーマ (migration 032)

- 6観点の 1536 列: `plot_embedding_1536` / `cast_embedding_1536` / `theme_embedding_1536` / `mood_embedding_1536` / `reader_embedding_1536` / `review_aspect_embedding_1536` (8,204件。変換・照合済み)
- 使うのは theme / mood / reader の3列 (似ているシリーズの計算)。plot / cast / review の3列も、将来のために残す
- 検索で使っていない単体ベクトル `embedding` / `review_embedding` (1536次元、HNSW あり) も **残す** (決定済み)
- 旧 3072 列は、本番を切り替えて1週間後に DROP する。それまでに、ローカルのバックアップ (`backend/backups/aspect_3072_20261015_094928/`) を取得・照合済み
- DB の変更は、CLAUDE.md の規約どおり dry-run と確認を先に行う

### 4.3 HNSW インデックス

- 6観点の 1536 列に HNSW (cosine、m=16、ef_construction=64) を作成済み (migration 033)
- **自然言語検索をやめたので、今は検索で使っていない**。似ているシリーズも `series_vectors` を全件または候補ごとに計算するので使わない。残すか消すかは §10-8

### 4.4 計算方法

| 機能 | 今の実装 (全件・インメモリ) | 新方式 |
|---|---|---|
| 似ているシリーズ | 6観点の cos を全件の中での順位にして合成。一番珍しいジャンルで絞る | ジャンル2つ以上同じ作品に絞り、theme / mood / reader の3観点の「候補の中での順位」で合成 (F8)。その場で計算 |
| おすすめ | 元にした作品ごとの cos の平均 → 順位にして合成 | 同じ考え方 (平均ベクトルとの近さ → 順位) を3観点で。その場で計算 (F10) |
| 自然言語検索 | 6観点のサブクエリで全件 | **作らない** |

- 計算は `series_vectors` (作品 id・著者・ジャンル・3観点のベクトルだけの細いテーブル、約151MB) に対して行う。共有バッファに収まるので、ディスクを読まずに済む
- `series_vectors` は、`openbd_test_series` のトリガーで自動的に同期する

### 4.5 データ更新の流れ

1. `*_text` を更新したら、`dimensions=1536` で埋め込み直して DB に書き込む (`reembed_aspects_large.py` を元に改修)
2. `series_vectors` はトリガーで自動的に更新されるので、作業は要らない
3. Next.js の `/api/revalidate` を呼び、キャッシュを捨てる
- `rebuild_vector_cache` (npz) は不要になり、廃止する

## 5. 非機能要件

### 5.1 性能 (Vercel 本番、p95)

| 処理 | 目標 |
|---|---|
| 一覧・キーワード検索 | 500ms 以下 |
| 詳細ページ (ISR キャッシュが効いているとき) | TTFB 200ms 以下 |
| 似ているシリーズ・おすすめ (RPC) | 500ms 以下 (実測: 似ているシリーズ p95 0.32秒、おすすめ 中央値 0.22秒。DB の再起動直後の1回目は数秒かかる) |

### 5.2 コストと悪用対策
- アプリから OpenAI などの有料 API は呼ばない (自然言語検索をやめたため)。そのため、API コストのためのレート制限やキャッシュの表は不要
- 入力に合わせた絞り込みは、300ms 待ってから送る (DB への負荷を抑えるため)

### 5.3 セキュリティ
- Supabase の service role key はサーバー側だけで使う。`NEXT_PUBLIC_` を付けない (アプリでは使わず、パイプライン専用)
- ユーザーのデータ操作 (お気に入り・読了・プロフィール) は、**ログインユーザーの JWT で Supabase を呼び、RLS で守る**。今のように「service key + 手動で user_id を確認」はしない
- RPC 関数は `SECURITY INVOKER` にし、公開データだけを返す。anon ロールに与える権限は必要最小限にする

### 5.4 SEO とアクセシビリティ
- 詳細ページは SSR/ISR。`sitemap.xml` を作る
- スマホ優先のレスポンシブ。キーボードで操作でき、画像に alt を付ける
- ライト / ダークの両方で、本文の文字は WCAG AA (4.5:1)、UI 部品と大きい文字は 3:1 以上のコントラストを満たす (ui-design.md §1.5)

### 5.5 運用
- デプロイ先は Vercel だけ。切り替えが終わったら Azure VPS と FastAPI を止める
- 環境変数: `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` / `REVALIDATE_SECRET`

## 7. 画面と API の対応

| 画面 / エンドポイント | 描画方式 | データ取得元 | 置き換える今の API |
|---|---|---|---|
| `/` | SSR (セクションはストリーミング) | RPC `recent_releases` + `recommend_for_me` | `/series/new`, `/users/me/recommendations` |
| `/search` | SSR + クライアントで絞り込み | RPC `search_series` / `facet_counts` | `/series/`, `/series/search`, `/series/tags` |
| `GET /api/search` | Route Handler | RPC `search_series` + `facet_counts` (並列) | — (新規。入力に合わせた絞り込み用) |

| `POST /api/revalidate` | Route Handler (シークレット必須) | — | — (パイプラインからのキャッシュ破棄) |
