# 作り直しで工夫したこと (説明用メモ)

就職活動などで、このアプリを説明するときのためのメモ。詳しい根拠は [architecture.md](architecture.md) にある。

## 1. 一言で

> 前のアプリでは、600MB のベクトルをメモリに載せた API サーバーを常に動かしていました。それを、**DB の中で計算する構成**に作り直しました。その結果、サーバーを持たずに Vercel だけで動き、外部 AI API の費用もかからず、データを更新するとすぐに画面に反映されるようになりました。

## 2. 前のアプリの課題

| 課題 | 何が困ったか |
|---|---|
| 検索に使う 600MB の行列 (6観点 × 3072次元、npz) を、API のプロセスがメモリに持っていた | サーバーレスにできない。2GB の VM を常に動かす必要があり、増やすこともできない |
| ベクトルを変えるたびに npz を作り直し、サーバーを再起動していた | データの更新が画面に反映されるまで手間がかかり、出し忘れも起きる |
| 自然言語検索で、1回の検索ごとに OpenAI (LLM + Embedding) を呼んでいた | 使われるほど費用が増える。設定やキャラを指定する検索 (「VRMMO」「悪役令嬢」など) は、30本中12本が0件だった |
| 一覧を出すたびに 1.7GB のテーブルを直接読んでいた | Micro プラン (共有バッファ 256MB) ではデータがメモリに残らず、遅い |
| 機能を足すたびに部品が増えた (VM、Caddy、npz、OpenAI、フロント用ホスティング) | 1つの不具合を追うのに、何か所も見る必要があった |
| SPA なので、検索の状態がブラウザの中だけにあった | 検索結果の URL を共有できない。最初の表示も遅い |

## 3. 工夫したこと (課題 → やったこと → 結果)

### 3.1 ベクトルを 3072 → 1536次元にして、DB に移した
- **やったこと**: 3072次元の先頭 1536 を切り出し、正規化しなおした。先に、この方法が埋め込み API の `dimensions=1536` 指定と同じになるかを確かめた。
- **結果**: API で作り直した場合とのコサイン類似度は 0.99987 で、埋め込みを作り直す費用がかからなかった。容量は半分になった。
- **安全策**: 移す前に、3072次元をローカルにバックアップした (582MB、sha256 で照合)。移行は件数を変えながら進むバッチで行い、途中から再開できるようにした。`updated_at` も動かさないようにして、データパイプラインの再開の仕組みを壊さないようにした。

### 3.2 計算に使う列だけの「細いテーブル」を作った
- **課題**: HNSW を作っても、元のテーブルが 1.7GB あるため、似ているシリーズの計算は2秒からタイムアウトになった。
- **やったこと**: 原因は、必要なベクトルが共有バッファに収まらないことだと突き止めた。そこで、計算に使う列だけを持つ `series_vectors` (約151MB) と、カード表示用の `series_cards` (約74MB) に分けた。どちらも元のテーブルのトリガーで自動的に同期する。
- **結果**: 似ているシリーズは p95 0.32秒、検索は 0.08〜0.24秒になった。プランを上げずに解決できた。

### 3.3 似ているシリーズを「タグで絞ってから、ベクトルで並べる」形にした
- **やったこと**: ジャンルタグが2つ以上同じ作品に絞り込んだ (GIN インデックスを使う)。その候補だけを、theme / mood / reader の3観点の近さで並べた。
- **結果**: 計算する件数は約4分の1 (中央値 2,127件) になり、結果を保存しなくても、その場で計算して間に合うようになった。前の方式の結果との一致率は 92%。

### 3.4 自然言語検索はあえてやめた
- **判断**: 費用、0件になる検索の多さ、メンテナンスの手間を比べ、タグ + キーワードの検索の方が利用者にとって確実だと判断した。
- **結果**: アプリからは有料 API を一度も呼ばないので、ランニングコストは DB とホスティング代だけになった。

### 3.5 API サーバーをなくし、ロジックを SQL の関数 (RPC) にした
- **結果**: FastAPI と VM、Caddy がいらなくなり、Next.js 1つで動くようになった。
- **セキュリティ**: 関数は呼んだ人の権限で動く (SECURITY INVOKER)。データは RLS で守られ、`recommend_for_me` も `auth.uid()` で本人の分しか読めない。このため、アプリに強い権限のキー (service key) を置かなくて済んだ。

### 3.6 Next.js 16 のキャッシュで、速さとデータの新しさを両立した
- 作品詳細などは `'use cache'` でキャッシュする。データパイプラインが DB を更新したら `/api/revalidate` を呼び、タグ単位でキャッシュを捨てる。
- ログインやランダム表示のように中身が毎回変わる部分だけを、Suspense で分けてリクエストごとに描く (PPR)。
- 検索条件は URL に入れるので、共有やブラウザの「戻る」ができる。

### 3.7 1つのコードから2つの版を出す
- 書影あり / 書影なし (あらすじ型) の UI を、環境変数 `NEXT_PUBLIC_UI_VARIANT` で切り替える。同じ機能と同じ DB のまま、見た目だけを変えて2つ公開できる。
- デザインのルール (角丸と影を使わない) は ESLint のルールにして、守れているかを機械で確かめる。ダークモードの配色はコントラスト比を確かめて選んだ。

### 3.8 useEffect を 15個から1個に減らした
- **前**: 15個あった。データの取得 (`fetch` → `setState`)、URL の値を state に写す処理、条件が変わったら1ページ目に戻す処理などを、すべて useEffect でつないでいた。state 同士が連鎖して描き直しが増え、取得の中止もしていなかったので、古い応答が新しい結果を上書きするおそれもあった。
- **今**: 1個だけ。入力を待つタイマーを、画面を離れるときに止めるためのもの。データの取得は Server Component で行い、検索の条件は URL を唯一の正とする。前の値と比べて描画中に直す処理と、`useTransition` で置き換えた。
- **言えること**: useEffect は「React の外のもの (タイマーなど) と同期するとき」だけ使う、という React 公式の方針に沿って設計した。

## 4. トレードオフ (正直に言えること)

| 選んだこと | 引き換えにしたこと |
|---|---|
| DB の中で計算する | 計算の負荷が DB に集まる。アクセスが増えたら Supabase のプランを上げる必要がある |
| ロジックを SQL の関数に置く | Python よりテストとデバッグがしにくい。変更は migration として管理する |
| 自然言語検索をやめる | 「こういう話が読みたい」という曖昧な探し方はできない |
| 細いテーブルを作る | 同じデータを二重に持つ。同期はトリガーに任せている |

## 6. 聞かれそうな質問

- **なぜ作り直したのか?** → 機能を足し続けた結果、**コードと構成が複雑になりすぎ、1つ直すのに何か所も見ないといけなくなった**から。
  - 例1: 検索の処理が3か所に分かれていた。ブラウザ (状態)、FastAPI (numpy の計算と、`vector_search.py` 444行)、OpenAI (クエリの分割) の3つで、検索の結果がおかしいときに、どこが原因かを追いにくかった。
  - 例2: キャッシュが二重になっていた。DB のベクトルを npz ファイルに保存し、起動時に読み込む。古くなったら作り直して再起動する。DB とキャッシュのどちらが正しいかを、いつも気にする必要があった。
  - 例3: 1つの画面を出すのに、API の中で何回もクエリを組み合わせていた。たとえば一覧のあとに、書影を別のクエリで付け足していた (`_attach_latest_covers`)。また、ログインの確認を全部のエンドポイントで自前で行っていた。
  - 例4: 使わなくなったものが残っていた。廃止した検索の API、Twitter 連携、試作用のスクリプト十数本、旧テーブルなどで、どれが今も使われているのかが分かりにくかった。
  - そこで、**「データの計算は DB、画面は Next.js」の2つに役割を絞って**作り直した。検索の結果がおかしければ SQL の関数を、画面がおかしければ Next.js を見ればよい。DB のトリガーで同期するので、キャッシュの作り直しもいらなくなった。
  - 注意: コードの行数は減っていない (前: フロント約2,100行 + API 約1,200行、今: TypeScript 約3,600行)。減ったのは**動く部品の数と、データの通り道の数**。画面と機能を増やしたので行数は増えたが、1つの処理を追うときに見る場所は減った、と説明する。
- **なぜ 1536次元にしたのか?** → 精度はほぼ変わらず (cos 0.99987)、容量とメモリが半分になるから。HNSW も、pgvector では 2000次元までしか作れない。
- **HNSW を作ったのに使っていないのはなぜ?** → 実際に測ると、タグで候補を絞ってから全件を計算する方が、この件数とプランでは速くて結果も安定していたから。将来ベクトル検索を戻すときのために残している。
- **一番苦労したことは?** → 似ているシリーズが遅い原因を、インデックスではなく「テーブルが太くてメモリに乗らないこと」だと突き止めたこと。インスタンスのメモリとテーブルのサイズを実際に測ってから、細いテーブルに分けることに決めた。
